## 1. 为什么需要集合通信

深度学习的三种并行方式都靠集合通信把各个设备"缝"起来：

| 并行方式 | 通信需求 | 对应集合通信 |
|---|---|---|
| 数据并行（DP） | 各卡算完梯度后求平均 | **AllReduce** |
| 张量并行（TP） | 切开的权重在各卡间拼/拆 | AllGather / ReduceScatter |
| 专家并行（EP） | token 按路由送到专家所在卡，算完再收回 | **AllToAll**（dispatch / combine） |
| FSDP / ZeRO | 参数分片、梯度分片 | AllGather / ReduceScatter |

**"集合"的含义**：所有 rank 共同参与、必须全员到齐才能完成。这也正是容错难做的原因——**一个 rank 出问题，整个集合操作就卡住了**。

---

## 2. 基本概念

| 概念 | 说明 |
|---|---|
| **rank** | 一个进程的编号（0..n-1）。一般一个 rank 绑一张卡 |
| **local rank** | 节点内编号（0..7），用于定位卡 |
| **world / world size** | 全局 rank 数与总数 |
| **通信域 / communicator** | 一组 rank 组成的通信上下文，持有连接、缓冲、拓扑、算法选择等状态。**资源开销大，创建代价高**（这是"能挂起恢复就别销毁重建"的原因） |
| **group / 子通信域** | 通信域的子集，可嵌套 |
| **out-of-place / in-place** | 输出缓冲是否与输入复用。**影响容错可行性**：输入被覆盖后就没法重算了（见 `02` 里 OpRetry 的约束） |
| **单算子模式 / 图模式** | 每次都走一次 host 编排 vs 整图下发。图模式下 host 不介入，**很多容错手段（如 OpRetry）不支持图模式** |

## 3. 集合通信操作族

| 操作 | 语义 | 通信量（n 卡，数据量 S） | 典型用途 |
|---|---|---|---|
| **Broadcast** | 一个 rank 的数据发给所有人 | S | 参数初始化 |
| **Reduce** | 所有人归约到一个 rank | S | — |
| **AllReduce** | 所有人归约，结果所有人都有 | 2S·(n-1)/n | 梯度平均（DP） |
| **AllGather** | 每人的分片拼起来，所有人都有完整数据 | S·(n-1)/n | 参数收集（FSDP） |
| **ReduceScatter** | 归约后按人切分，各拿一片 | S·(n-1)/n | 梯度分片（ZeRO） |
| **AllToAll** | **每个人给其他每人各发一份不同的数据** | S·(n-1)/n | **MoE 专家并行**（本任务目标） |
| **AllToAllV / VC** | 变长版（各人收发量不等）/ 用矩阵指定 | 视情况 | MoE 里 token 分布不均（真实场景就是不等长） |
| **Scatter / Gather** | 一对多分发 / 多对一收集 | S·(n-1)/n | — |
| **Send / Recv** | 点对点 | S | 流水线并行 |
| **Barrier** | 全局同步 | ~0 | 同步点 |

> **AllToAll 的特殊性**：AllReduce/AllGather 里，任意一份数据都能从别的 rank 的信息里"推"出来（或至少校验）；**AllToAll 里每个数据块都是独一无二的，任何别的 rank 都没有它的副本，也无法推导**。这就是容错难度的分水岭。

### AllReduce 的两阶段分解（理解 ring 算法的基础）
```
Ring AllReduce = ReduceScatter（把总和按人切片）+ AllGather（把切片拼回完整）
```
每一步每个 rank 只发 `S/n` 数据，共 `2(n-1)` 步 → 总通信量 `2S(n-1)/n`，**与卡数 n 无关地逼近 2S**，这就是 ring 算法的带宽最优性。

## 4. 集合通信算法

同一个语义有不同算法，**选哪个取决于消息大小和拓扑**：

| 算法 | 步数 | 特点 | 适合 |
|---|---|---|---|
| **Ring（环）** | 2(n-1) 步 | 带宽最优，时延随 n 线性增长 | **大消息** |
| **Tree（树）** | 2·log n 步 | 时延最优，带宽利用率差 | **小消息** |
| **Halving-Doubling（递归倍增）** | log n 步 | 时延好、数据分片交换 | 中小消息 |
| **NHR / 2D-Torus 等** | — | 针对特定拓扑（分层、超节点）优化 | HCCL 里大量存在 |

**关键指标**：
- **algbw（算法带宽）= 数据量 / 耗时**：从用户视角的有效带宽
- **busbw（总线带宽）= algbw × (n-1)/n**：硬件视角的实际链路带宽，用于和硬件峰值比
- 小消息受**时延**支配，大消息受**带宽**支配 → 这是算法选择的根本依据

> HCCL 的算法选择由 `cost_model` + `topo_match` 自动完成，见 `02-HCCL架构.md`。

## 5. 同步与数据搬运（昇腾语境）

通信算子内部做的事其实只有三类，理解这一点对做容错很关键：

| 类别 | 昇腾上的手段 | 说明 |
|---|---|---|
| **算** | AI Core（Vector / Cube 单元） | 归约、格式转换等计算 |
| **搬** | **SDMA**（片内/卡间）、**RDMA/RoCE**（跨节点网络）、**HCCS**（卡间高速互联）、**UB**（超节点总线） | 数据搬运 |
| **同步** | **notify / wait** | 通知对端"我发完了"/等待对端信号 |

> 所以"通信算子"的 kernel 里同时有计算指令和通信指令，它本质是**一个带通信指令的并发程序**，不是纯计算核。
> 也正因如此，**Triton 这类只表达计算的 DSL 无法实现 all2all 的搬运部分**（详见 `00` 的 C8 条）。

## 6. 软件栈分层（昇腾）

```
上层框架（PyTorch / MindSpore）
        ↓  torch.distributed / 框架通信 API
集合通信库  ← HCCL（本任务主战场）
        ↓
通信平台/传输层 ← HCOMM（hcomm 仓库）
        ↓
驱动 / 固件 / 互联硬件（HCCS、RoCE 网卡、UB）
```

⚠️ **实务要点**：`code/hccl` **只包含算子与算法层**，通信域生命周期实现在 hcomm（通过 `src/common/hcomm_dlsym/` 弱符号动态加载）。**涉及通信子创建/销毁/缩容的改动，要动 hcomm。**
