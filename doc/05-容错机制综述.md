## 1. 第一步：定义故障模型

**没有故障模型就没有容错设计。** 问自己（和导师）这几个问题：

| 故障类型 | 表现 | 检测难度 | 恢复难度 |
|---|---|---|---|
| **fail-stop** | 进程/节点直接挂掉、退出 | 易（连接断、超时） | 中 |
| **hang / straggler** | 卡死不报错、掉队 | **难（必须心跳 + 超时）** | 难 |
| **静默数据错误（SDC）** | 数据错了但没人报错 | **极难（只能靠校验和）** | 难 |
| **链路瞬断** | 网络抖动、丢包 | 中（RDMA 层通常自己重传） | 易（多数被下层吸收） |
| **性能降级** | 卡变慢、网络降速 | 中 | 视情况 |

### 恢复语义（同样必须定义）
| 语义 | 含义 | 代价 |
|---|---|---|
| **checkpoint-restart** | 存盘、全批重启 | 停机时间长，但实现最简单 |
| **mask-and-continue** | 屏蔽故障参与者继续跑 | 语义会变（少了一部分数据/计算） |
| **缩容降级（shrink）** | 摘掉死掉的 rank，用更小的通信子继续 | 需重排分片、需上层补偿语义 |
| **冗余接管** | 备用副本顶替 | 需要预留资源（冗余专家） |
| **挂起 + 上层决策（suspend/resume）** | 通信库只保证不卡死、状态可保存，由框架决定怎么办 | 库实现复杂，但最灵活 |

> ⭐ **A2 已定"参考新一代"** → 恢复语义 ≈ **尽量不中断 + 缩容降级继续**，而不是全批重启。

## 2. 第二步：按三层拆解任何容错方案

看任何论文/代码，都按这三层问一遍：

```
【检测层】怎么发现出事？
   ├─ 异步错误查询（调用返回"进行中"，需轮询）
   ├─ 超时 / 看门狗
   ├─ 心跳（集群级）
   └─ 错误聚合：让所有 rank 对"谁死了"达成一致 ← 极易被忽略但必不可少
        （否则有的 rank 在 abort、有的还在发数据 → 死锁/数据错乱）

【在途处理层】已经飞出去的数据怎么办？
   ├─ 中止（abort）：丢弃，配合重建
   ├─ 挂起（suspend）：保留状态，等决策
   ├─ 重传：只重发未确认的部分（最优但最难）
   └─ 重执行：整个算子重跑（HCCL 的 OpRetry 就是这个）

【恢复层】成员怎么变？
   ├─ 缩容（shrink）/ 扩容（grow）
   ├─ 冗余顶替
   └─ 销毁重建
```

## 3. AllReduce 上的容错手段（以及为什么不能照搬到 AllToAll）

### 3.1 AllReduce 可用的手段【通识】
| 手段 | 原理 |
|---|---|
| **ABFT / 校验和** | 数据附带校验和，用**数学冗余**算出丢失 rank 的贡献并重构结果，不用重启 |
| **冗余 rank / 热备** | 多算一份，或用备用卡顶替（如用备份网卡预注册同一 DMA buffer） |
| **checkpoint-restart** | 周期性落盘，失败后整体回滚重算 |
| **超时 + 缩容** | 剔除故障 rank，用更小的通信子继续 |
| **重传（分块 + 确认）** | 从"最后确认的块"开始重发 |

### 3.2 ⭐ 为什么这些几乎都不能用在 AllToAll 上

**核心差异：数学冗余的有无。**

- **AllReduce 有余数学冗余**：结果 = 所有 rank 贡献的**和**。加法的可交换/可结合性意味着：
  - 任意子集的和都是"部分信息"，缺的那一份可以用别的独立线性组合（校验和）**解出来**
  - 所以丢一个 rank 的贡献，**可以从其他 rank 的信息重构**
- **AllToAll 没有数学冗余**：A 发给 B 的那块数据，**只有 A 有**；任何其他 rank 既没有副本，也无法推导。丢了一个 rank，就是**整行/整列数据永久缺失**。

**推论（本任务的理论基础）**：
> AllToAll 的容错**只能走协议层**：可靠投递（重传）+ 完成度跟踪 + 成员变更（缩容）+ 分片重排 + 语义补偿。
> 不可能有"优雅的数学重构"路线。**这也意味着这个题目有真实的研究空间**——NCCL/HCCL 都没有现成的好方案。

⚠️ 另有一个陷阱：AllToAll 的**分片布局与全局成员绑定**（每人给每人的那一块，位置按成员顺序排）。**一旦缩容，布局全部要重算**，这不是"继续跑"，而是"换一套语义重新跑"。所以：**缩容后丢失的数据由谁负责补偿，必须由上层框架决定**——这正是分工边界（A4）落在"只做通信层"的原因。

## 4. NCCL 的容错能力【源码核实，NCCL 2.32.3】

### 4.1 确认存在的设施

| 设施 | 证据（克隆源码路径） | 作用 |
|---|---|---|
| **`ncclCommShrink`** | `src/nccl.h.in`、`docs/userguide/source/usage/communicators.rst:143-184` | 从现有通信子"排除若干 rank"创建新通信子。flag：`NCCL_SHRINK_DEFAULT` / `NCCL_SHRINK_ABORT`（后者先中止在途操作） |
| **`ncclCommGrow`** | 同上，`:189-283` | 往现有通信子**加入**新 rank 创建新通信子（老 rank 传 NULL uniqueId，新 rank 用 `growId`） |
| **`ncclCommGetAsyncError`** | `docs/userguide/source/usage/communicators.rst:102`、`contrib/nccl_checkpoint/shim_core.h:169` | 非阻塞通信子的异步错误查询（官方推荐的容错配方：非阻塞 + 轮询 + `ncclCommAbort` + 重建） |
| **RAS 子系统** | ✅ **确实存在**：`src/ras/ras.cc`、`src/ras/diagnostics_paths.cc`、`src/include/ras.h`；文档 `docs/userguide/source/troubleshooting/ras.rst`、`docs/userguide/source/env.rst`；**官方例子** `docs/examples/08_ras/01_fault_detection/` | 可靠性子系统：检测挂死/掉队的 rank |
| **`contrib/nccl_checkpoint/`** | `shim.cc`、`shim_checkpoint.cc`、`gen_shim.py` | **通信子 checkpoint/restore 垫片**：拦截并记录 `ncclCommShrink`（父通信子、被排除 rank、flags）以便恢复；`gen_shim.py` 里明确把 shrink/grow 列为需要记录的操作 |
| **`contrib/nccl_ep/`** ⭐ | `nccl_ep.cc`（`ncclEpDispatch`:2820、`ncclEpCombine`:3653、`ncclEpGroupDestroy`:1785）、`ep_bench.cu`、`ep_test.cu`、`README.md`、`include/nccl_ep.h` | **NVIDIA 官方 EP（专家并行）库**：`libnccl_ep.so`，版本 0.1.0，提供 dispatch/combine API、EP group 生命周期、benchmark 与测试 |

### 4.2 官方文档里明确的**约束**（做方案时必须知道）

- `ncclCommShrink`：**只有将要留在新通信子里的 rank 才调用**它
- `ncclCommGrow`：父通信子上**不能有任何未完成的操作**，否则可能死锁
- 非阻塞通信子 + 异步错误 + abort + 重建：官方推荐的容错路径

### 4.3 ✅ 已定论：`ncclCommSuspend/Resume` 是显存 offload，**不是**错误恢复

**源码证据**：
- 实现位置：**`src/mem_manager.cc:992-1070`**（注意是 **mem_manager**，不是错误处理模块）
- 头文件定义：`src/nccl.h.in:416` → `#define NCCL_SUSPEND_MEM 0x01  // Suspend memory (release dynamic allocations)`
- 日志措辞：`"ncclCommSuspend: rank %d suspending memory"` / `"ncclCommResume: rank %d resuming all resources"`
- 签名：`ncclResult_t ncclCommSuspend(ncclComm_t comm, int flags)` / `ncclResult_t ncclCommResume(ncclComm_t comm)`
- Python 绑定侧是**动态加载**的（`bindings/nccl4py/…/nccl_linux.pyx:1423/1433`，找不到就报 `FunctionNotFoundError`）→ 说明不是所有版本/构建都提供。

> ⚠️ **结论**：**别被名字误导**。NCCL 的 suspend/resume 是**显存管理**手段（释放通信子占用的动态显存），**与容错无关**。
> 对照：**HCCL 的 Suspend/Resume 才是真·快恢**（见 `02-HCCL架构.md` §5.2）。两者名字一样、语义完全不同——这是本任务里最容易踩的坑。

### 4.4 【调研，待核】NCCL 容错能力的引入版本

调研得到（**尚未逐条核对官方 release notes**）：RAS 在 2.24 引入且默认开启（`NCCL_RAS_ENABLE`）；`ncclCommShrink` 在 2.27；`ncclCommGrow` 在 2.29.2。**我们手上是 2.32.3，这些都已在源码中确认存在。**

## 5. Meta 的路线：FT-HSDP 与 FTAR【调研 + 论文原文待读】

论文：**《Training LLMs with Fault Tolerant HSDP on 100,000 GPUs》**（arXiv:2602.00277，PDF 在 `doc/papers/`）

**核心思想**：**以数据并行副本（replica）为容错单位**——单个副本故障时只重启该副本，其余副本继续训练。

**两个关键机制**：
1. **FTAR（fault-tolerant all-reduce）**：**CPU 驱动成员增删，GPU 只负责传数据**。
   → 控制平面与数据平面分离。这是**最值得抄进 AllToAll 方案的设计决策**。
2. **非阻塞 catch-up**：恢复的副本**先发零梯度占位**，不阻塞其他 rank 的通信，再逐步对齐。

**论文数据（待核）**：恢复停顿 10min → 3min；有效训练时间占比 44% → 80%。

**配套库**：**torchft**（`code/torchft`），提供容错的 DDP/HSDP 进程组、Lighthouse 协调、P2P checkpoint 传输。

**同族论文**：**NCCLX**《Collective Communication for 100k+ GPUs》（arXiv:2510.20171），含 FTAR 与 Fault Analyzer。

> ⚠️ 读论文时**务必把两层分开**：
> - **算法层冗余**（参数/优化器状态有 DP 副本 → 死一个能从别处重建）
> - **通信层 FT**（只保证不卡死、可挂起、可缩容，**不负责重建数据**）
> 本任务（A4 已定）落在**通信层**。

## 6. MoE 的算法层容错：冗余专家 / EPLB【通识 + 昇腾线索】

在 MoE/EP 场景里，容错还有一条**算法层**的路子——**冗余专家**：

- 每张卡上**额外多放几份专家副本**（不只放自己要用的）
- 某张卡挂掉后，它负责的专家由**副本**接管
- 配合 **EPLB（Expert Parallel Load Balancer）** 做负载均衡 + 故障接管

**昇腾上的落点**：`code/ops-transformer/mc2/moe_update_expert/`（专家→物理卡映射、按阈值剪枝）。
检索关键词：`zeroExpertNum`、`sharedExpertRankNum`、`localMoeExpertNum`。

> **和通信层容错的关系**：冗余专家解决"**计算**不能停"，通信层容错解决"**数据搬运**不能卡"。两者互补，**你的任务是后者**。

## 7. 对 AllToAll 容错的设计启示（小结）

1. **控制平面 / 数据平面分离**（抄 FTAR）：成员变更、分片重排、语义补偿放 host/C++ 侧；kernel 只按计划搬运 + 上报状态。
2. **检测要与现有设施复用**，不要重造：HCCL 已有超时管理（`exec_timeout_manager`）和集群心跳；NCCL 侧对应 RAS。
3. **在途处理优先"挂起/中止 + 重建"**，而不是"保留状态精确恢复"——后者在 AllToAll 上极其困难（分片与成员绑定）。
4. **缩容必然改变语义**，必须由上层决定"丢失的数据怎么办"（丢弃/重路由/上层重算）。**这条要和导师明确写进接口约定。**
5. **重传的粒度**是关键设计点：整体重跑（简单，浪费）vs 分段确认后增量重发（复杂，省带宽）。
6. **性能判据**：容错路径在**正常时**的额外开销应接近 0（只有出错才付代价）。
