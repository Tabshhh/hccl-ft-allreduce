# 06 · 现有 AllToAll 库的容错横评 ★

> 来源：直接勘察 `code/nixl`、`code/mooncake`、`code/deep-ep`（2026-09-21 克隆后逐文件核对）。
> 勘察方式：定位 `elastic` / `active_ranks` / `mask` / `timeout` / `shrink` / `reconnect` 等关键词并读上下文。
> `【核实】`= 有明确文件路径的源码证据；`【未确认】`= agent 未逐行确认的点。
> 最后更新：2026-09-21

## 0. 三句话结论（先看这个）

1. ⚠️ **三家的 "elastic" 根本不是一回事**：**DeepEP 的 `ElasticBuffer` 是"弹性显存"（内存可配 CPU/GPU），完全不是容错**；nixl 的才是**真弹性**（成员增删 + 故障屏蔽）；mooncake 分两层（设备层屏蔽 + PG 控制面）。
2. ⚠️ **丢掉的 rank 的数据，三家一律"丢弃"** —— 没有重路由、没有从副本恢复、**没有任何重传逻辑**（找不到 ACK/重试路径）。冗余只存在于"专家选择"层面，**没有备用 rank**。
3. ⭐ **只有 mooncake 有独立的控制面**（Mooncake PG 的 coordinator：RankState 状态机 + reconciliation window），**最接近 NCCL RAS**；nixl 是"设备自治 + 应用编排"；DeepEP 基本没有。

> 🎯 **这张图对你最重要**：业界 EP all2all 的容错现状 = **"屏蔽 + 丢弃"**。**没有人解决"丢掉的数据怎么办"**。
> 这正是你题目可能的创新空间——**也是你必须先和导师对齐"容错到什么程度"的原因**（见 `99-问题清单.md` A3）。

## 2. nixl_ep —— 三者中最完整的"真弹性"

**对外接口**【核实】：`code/nixl/examples/device/ep/nixl_ep/buffer.py`
- `low_latency_dispatch(...)`(:329) / `low_latency_combine(...)`(:443)，`dispatch`/`combine` 是 LL 别名(:439, :522)
- `ht_dispatch`/`ht_combine`(:526, :663) —— 高吞吐变体
- 数据布局：`[num_local_experts, num_max_dispatch_tokens_per_rank*num_ranks, hidden]`；FP8 e4m3 + scale（可 UE8M0）；combine 支持 LogFMT
- kernel：LL `csrc/kernels/nixl_ep_ll.cu`、HT `csrc/kernels/nixl_ep_ht.cu`

**容错机制**【核实】：
| 环节 | 位置 | 做法 |
|---|---|---|
| 主机侧状态 | `csrc/nixl_ep.hpp:127-133` | `active_ranks` 位图 + `active_rank_bound` |
| 状态维护 | `csrc/nixl_ep.cpp:82-107`、`:1267-1304` | `set_active_rank_bound` / `_refresh_active_rank_bound` / `update_mask_buffer` / `query_mask_buffer` / `clean_mask_buffer` |
| 设备侧检测 | `csrc/kernels/nixl_ep_ll.cu:47-65`、`:319-338`(dispatch)、`:851-866`(combine) | 接收等待超过 `timeout_cycles` → `atomicExch(mask_buffer_ptr+src_rank, 1)` **自动屏蔽**；若 `mask_buffer_ptr == nullptr` 则 `trap()` |
| 触发者 | 两个 | (a) 应用/编排器调 `connect_ranks`/`disconnect_ranks`（`buffer.py:842-878`）<br>(b) **设备内核超时自治屏蔽** |
| 编排器示例 | `tests/elastic/plan.py` + `rank_server.py` | 演示了编排器角色 |

**对应 NCCL 的哪一层**：
- `connect_ranks`/`disconnect_ranks` ≈ **Grow / Shrink** 的连接建立与拆除
- `update_mask_buffer` ≈ **Shrink 的成员裁定**（但由应用显式调用，**不是集体协商**）
- LL 内核超时 → mask ≈ **RAS 异步检测 + 自动收缩**
- HT 路径 `trap()` ≈ 异步错误直接 abort
- **缺**：Grow 之后的集体重建层（由应用负责重连）

## 3. mooncake-ep —— 唯一有独立控制面的实现

**分两层，务必区分**（这是最容易读错的地方）：

### (A) 设备层屏蔽 —— **只在 legacy LL 内核里**
`mooncake-ep/src/mooncake_ep_kernel.cu:419-433`(dispatch) / `:688-731`(combine)：`timeout_ticks` 到期 → `active_ranks[src_rank]=0`，该 rank 按 0 token 处理并被跳过。测试：`python/tests/ep/test_ep_grid.py:151-157, 362`。

### (B) 控制面 —— **Mooncake PG**（这才是 RAS 等价物）⭐
- 状态机：`mooncake-pg/src/control_plane/coordinator.cpp:67-113, 389-407` → `RankState{Healthy, Offline, Synced, Inactive}` + reconciliation 窗口开闭
- 超时配置：`mooncake-pg/src/mooncake_communicator.cpp:278-307` → `setCollectiveTimeout` / `setP2PTimeout` / `setFaultReconciliationWindow`
- 成员变更：同文件 `:1423-1468` → `deactivateRanks` + **in-place rejoin**
- 自动策略：`mooncake-pg/torch/include/mooncake_backend.h:57-78` → `autoDeactivateOnFailure_` / `autoSyncOnFailure_`
- Python 接口：`torch/src/pg_py.cpp:307` `get_active_ranks`、`:313` `deactivate_ranks`、`:272/:282-289` 存活探测与故障协调窗口

### 桥接与 ⚠️ 重要陷阱
- 桥接：`python/mooncake/mooncake_elastic_buffer.py:471-485` `_active_ranks_mask()` 从 PG 读 mask → `:602-611, 625-626` 传给 `sync_ibgda_peers` / `sync_nvlink_ipc_handles`；`:559` 在 active_ranks 变化时 `update_local_qpns()`（重造 QP，实现在 `mooncake-ep/src/mooncake_ep_buffer.cpp:541-547`）
- ⚠️ **新的 elastic 路径其实忽略了 `active_ranks`**：`mooncake-ep/src/mooncake_ep_elastic_buffer.cpp:964` 与 `:1032` 是 `(void)active_ranks;`；Python 侧注释明确写 **"native elastic kernels currently use fixed communicator membership"**
- ⚠️ 走 NCCL 后端时更严格：`mooncake_ep_elastic_buffer.cpp:684-690` 的 `update_local_qpns` 直接**抛错** "membership is fixed; recreate the buffer instead"；只有 `reconfigure_nccl`(:605) 才走 NCCL 的 `update_ep_member()`

**对应 NCCL**：PG coordinator/agent + RankState 状态机 ≈ **RAS 检测与仲裁**；`deactivate_ranks` ≈ **Shrink**；`reconfigure_nccl` ≈ **异步错误后通信器重建**；`sync_ibgda_peers` + `update_local_qpns` ≈ **传输层重连**；内核 `active_ranks` 屏蔽 ≈ **把 RAS 结论下发到 kernel**（仅 legacy 路径生效）。

## 4. DeepEP —— 新路径没有容错（重要提醒）

| 路径 | 容错情况 |
|---|---|
| **新 `deep_ep.ElasticBuffer`**（`deep_ep/buffers/elastic.py`）| ❌ **完全没有容错**。全文无 `active_ranks`/mask/shrink；`elastic.py:245` 的 `num_cpu_timeout_secs`/`num_gpu_timeout_secs` 只是 **CPU/GPU 同步超时**，超时即失败，与成员管理无关。**"Elastic" 指显存弹性（GB/CPU/混合）** |
| **legacy `deep_ep.Buffer(enable_shrink=True)`** | ✅ 有：`deep_ep/buffers/legacy.py:42/60/91` + `:672-698` 的 `low_latency_update_mask_buffer`/`query`/`clean`；C++ 侧 `csrc/legacy/buffer.hpp:1731-1748`；设备实现 `csrc/kernels/legacy/internode_ll.cu:10-17, 386-404, 954-968, 1241-1284`（同样是**超时 → mask**） |
| HT / legacy internode | ❌ 只有 `LEGACY_NUM_TIMEOUT_CYCLES`（`csrc/kernels/legacy/compiled.cuh:18`，约 100 s）→ printf / `trap`，**无 mask** |

**数据重排**：同为丢弃。**无**成员变更协商、无重连、无备用 rank、无心跳。
注意：`tests/elastic/test_ep.py:598 --masked-ratio` 只是**造 `-1` 的 topk**，和 rank 故障无关——**别被测试名字误导**。

## 5. 把三方映射到"检测 / 在途 / 恢复"三层

| 层 | nixl_ep | mooncake-ep | DeepEP |
|---|---|---|---|
| **检测** | 设备侧超时（30 s 默认） | 设备超时 **+ PG 心跳/存活探测 + 协调窗口** | 设备侧超时（legacy LL）；HT 仅 ~100 s 后 trap |
| **在途** | 超时 → 置 mask 位 → 跳过继续 | **两层**：设备置 `active_ranks=0`；PG 做状态裁定 | legacy：置 mask；HT：trap 中止 |
| **恢复** | 成员变更由**应用/编排器**调 `connect/disconnect_ranks`；无集体重建 | PG `deactivateRanks` + in-place rejoin + **QP 重造**（最完整） | ❌ 无 |

## 6. 空白点 = 你的机会 ⭐

综合四方（NCCL / nixl / mooncake / DeepEP）+ 昇腾现状，**业界共同的空白**：

1. ❗ **"屏蔽之后丢失的数据怎么办"没人解决** —— 全是丢弃。上层模型会看到"某些 token 的专家输出缺失"。**这是一个真正的开放问题。**
2. ❗ **没有重传机制**：四家都找不到 ACK/重试路径。AllToAll 在途数据的**分段确认 + 增量重传**是空白。
3. ❗ **没有"备用参与方"**：没有备用 rank、没有冗余 expert 的通信层配合（冗余只存在于专家选择层面，见 `mooncake-ep/include/elastic/mooncake_ep_elastic_dispatch_official.cuh:106` 注释 "Expert choice can not be redundant"）。
4. ❗ **控制面与数据面的接口不统一**：nixl 靠应用编排、mooncake 靠 PG、DeepEP 没有——**没有事实标准**。
5. ❗ **昇腾侧的对应物**：HCCL 有 OpRetry（整算子重跑）+ Suspend/Resume（快恢，但**本仓库内没找到缩容**），ops-transformer 的 dispatch v2 有 `moe_distribute_elastic.h`（EP 域缩容）。**这三者之间怎么串起来，是你要回答的问题。**

## 7. ⭐ 谁做了"专家摆放"？（2026-09-23 新增调研）

**问题**：成员变更/故障之后，"**新的专家→卡映射**"是谁算的？

| 库 | 专家摆放（算表）| 具体到什么程度 |
|---|---|---|
| **vLLM Elastic EP** | ✅ **完整做了** | **但没有第二套算法**——复用 EPLB 的 `rebalance_experts`，**只把缩小后的拓扑当参数传进去** |
| **SGLang EEP** | ⚠️ **方向更正确** | 把故障掩码 `active_ranks` **直接作为算法入参**（比 vLLM 更 fault-aware）；**但 `elasticity_aware.py` 的算法体未确认**（网络受限）→ **不可照抄** |
| **mooncake-ep** | ❌ | 只管通信成员（`mooncake-pg` 树 grep `expert` **零命中**）|
| **nixl_ep** | ❌ | 只管建拆连接；专家数由调用方自己算（测试里直接 `专家数/卡 × 当前卡数`）|
| **DeepEP** | ❌ | 只 mask，不摆放 |

### vLLM 的做法（可参考的正解）

路径：`vllm/distributed/elastic_ep/elastic_execute.py:605` → `eplb_state.py:810-821` → `rebalance_execute.py:508`

1. 构造 `rank_mapping = {旧卡号: 旧卡号 if 存活 else -1}`（`perform_scale_down_eplb_reshuffle`）
2. **只换三个拓扑参数**（weight 仍用原负载窗口）：`num_gpus = 存活卡数`、`num_replicas = num_replicas // ep_size * num_gpus`、`num_nodes = 存活卡数所在节点数`
3. **重跑同一个** `policy.rebalance_experts(...)` —— **没有为故障写新算法**
4. 用 `rank_mapping` 算 src→dst 搬运（`_map_{old,new}_expert_indices_with_rank_mapping`），跳过 `-1`

**两个重要事实**：
- **缩容不是自动检测的**：由**外部控制器显式下发** `ReconfigureDistributedRequest`
- **强制前置**：`vllm/config/parallel.py:910` 要求 `enable_eplb=True` 才能用 Elastic EP

### 昇腾侧参考时要注意的约束

1. 强依赖 EPLB 已开启；靠 `preserve_intragpu_slots` 压低搬权重开销
2. `balanced_packing` / `replicate_experts` 是 **numpy CPU 实现 + 逐 layer 双重循环** → 规模大时是 **CPU 瓶颈**
3. `num_groups % num_packs != 0` 会**退化到全局模式**，均衡性下降（对应"缩容后卡数不整除"）
4. **失效卡的负载仍被计入**（负载 all-reduce 在缩容前的完整 EP 组上做）→ **摆放不是故障感知的**；要做"把死卡负载清零"需自行扩展
5. `eep_reconfigure.py` 只为新 EP size 重建 kernel（staging），**不含摆放数学**；`expert_map_manager.py` 是初始化期静态切分，也不是 EEP 的摆放计算器

## 8. ⭐ mask 与重排：不是二选一，是两个层次（2026-09-23）

**常见误解**："有的方案 mask 就行，有的要费劲搬移" —— 其实它们**不在同一层**：

| 层 | 能力 | 解决什么 | 谁有 |
|---|---|---|---|
| **通信/算子层** | **mask**（跳过失效 rank）| "**通信不能卡**" | ✅ **所有库都有**（nixl_ep / mooncake-ep / DeepEP / vLLM 的后端）|
| **框架/控制面层** | **重排**（重新分配专家）| "**精度不能掉**" | ✅ **只有 vLLM / SGLang** |

准确说法：**所有库都在下层做了 mask，只有 vLLM/SGLang 多做了上层。**

### 为什么 mask 有代价
- mask 之后，本该发给失效卡的那批 token，**那部分专家计算就没了**
- 好在 **MoE 的 topK 机制天然容忍**：少一两个专家可用剩下的加权近似，**精度掉但不会崩**
- **但推理服务对精度敏感** → vLLM/SGLang 选择再补一层：把失效卡的专家重新分配到存活卡

### ⭐ 标准答案是分阶段，不是二选一（SGLang 就是这么做的）
```
故障发生 → ① mask（微秒级，立刻止住，精度暂时受损）
         → ② 算新映射 + 搬专家（秒级）
         → ③ 按新映射继续（精度恢复）
```
SGLang 的 kernel 有 `active_ranks` mask（止住），EPLB 用 `elasticity_aware` 按 `active_ranks` 重排（恢复）—— **两层配合**。

### 昇腾侧的对应（判断依据）
| 阶段 | 昇腾现状 |
|---|---|
| ① mask 止损 | ⚠️ **待确认**：昇腾的 `x_active_mask` 是 **token 级**的（表示"这个 token 参不参与通信"），**rank 级的屏蔽机制尚未找到** —— 要查 |
| ② 重排恢复 | ❌ 没人做（**这是任务核心**），但接口预留好了 |
| ③ 按新映射继续 | ✅ 官方写好了（`isScalingDownFlag_` 分支）|

**为什么判断昇腾走"重排"路线**（三条硬证据）：
1. **`elasticInfo` 接口存在的意义就是接收新映射** —— 没有重排，这个接口毫无用处
2. **`moe_update_expert` 算子就是 EPLB 的落地** → 昇腾有重排的基础设施
3. **infershape 会按新成员重算输出 shape** → 设计上就预期"成员会变"
