## 0. 一句话结论

**"弹性 EP / 容错 EP" 指的是 AllToAll（dispatch/combine）层面，不是 AllReduce。**

vLLM 已有官方 **Elastic EP** 路线（detect → scale_down → scale_up），SGLang 用 Mooncake EEP 已跑出实测数据；**而昇腾侧这条线还没有落地**——**这就是你的任务位置。**

## 1. 术语澄清（这一条纠正了一个常见误解）

| 说法 | 实际含义 | 出处 |
|---|---|---|
| vLLM "Elastic EP" | EP 域的**检测 → 缩容 → 扩容** | vLLM 博客 2026-05-14【多方印证】 |
| vLLM "FT-EP" | **dispatch/combine kernel 的 mask 支持矩阵** | RFC #27774【多方印证】 |
| SGLang "elastic EP" | 故障容忍的 MoE A2A 后端 | SGLang EP 文档【多方印证】 |
| **AllReduce 的角色** | **必须绕开/替换的配套依赖，不是 EP 弹性的实现层** | RFC #40567、RFC #30112（gap A）、SGLang 要求 `--disable-custom-all-reduce`【多方印证】 |

**一个很有价值的工程细节**：vLLM PR #44428 的故障注入显示——**先出现 DP allreduce 超时，之后才暴露 EP all2all kernel 超时**。说明做 EP 弹性时，**会先被 AllReduce 挡住**。

## 2. vLLM 的 EP 与弹性

### 2.1 EP 接入
- `--enable-expert-parallel`（bool，默认 false）
- `--all2all-backend`（对应 `vllm/config/parallel.py` 的 `all2all_backend` 字段；旧环境变量 `VLLM_ALL2ALL_BACKEND` 已弃用，源码提示 "will be removed in v0.15.0"）
- 后端取值（**随版本变化，待核实**）：`allgather_reducescatter`（默认）、`naive`、`pplx`、`deepep_high_throughput`、`deepep_low_latency`、`mori`、`nixl_ep`、`flashinfer_*`
- 接线位置：`vllm/distributed/device_communicators/all2all.py`，每个 backend 一个 manager
  - 例：`DeepEPV2All2AllManager` 用的是 **DeepEP v2 的 `ElasticBuffer` + NCCL Gin**

### 2.2 EPLB 与冗余专家
- `--enable-eplb`（必须配 EP，否则报错 `enable_expert_parallel must be True to use EPLB`）
- **冗余专家数量在 `--eplb-config` 里**：`num_redundant_experts`（默认 0）；`n_physical = n_logical + n_redundant`
- 谁决定副本位置：`rebalance_experts(weight, num_replicas, num_groups, num_nodes, num_ranks, old_global_expert_indices)` → 输出 `physical_to_logical_map`（`vllm/distributed/eplb/policy/`，默认实现 balanced_packing，沿用 DeepSeek EPLB 思路）

⚠️ **关键：EPLB 自己撑不住故障**（RFC #40567）：EPLB 控制面的三个集合通信（NCCL all_reduce、Gloo all_reduce、Gloo monitored_barrier）在**任一 EP rank 死亡时无限阻塞，并永久 poison 进程组**。

→ 所以 vLLM 的官方路线是 **Elastic EP（不是 EPLB）**：**detect → scale_down → scale_up**，
   **NIXL-EP 提供 EP 侧的故障检测与 `connect_ranks` / `disconnect_ranks`**。

### 2.3 ⭐ 一个重要的串线发现

**导师给的那三个资源（nixl-ep / mooncake-ep / deep-ep）不是随便列的 —— 它们就是 elastic EP 的后端生态。**

| 资源 | 在弹性 EP 里的角色 |
|---|---|
| `nixl_ep` | vLLM Elastic EP 的成员管理原语提供方（`connect_ranks`/`disconnect_ranks`）——**这正是我在 `doc/06` 里独立勘察到的同一套接口** |
| `mooncake-ep` | SGLang 的 EEP 后端 |
| `DeepEP` | vLLM 的 `deepep_*` 后端（其 v2 `ElasticBuffer` 被 vLLM 采用）|

> **所以围绕这几个库做容错调研，方向从一开始就是对的。** 这条可以写进给导师的汇报里。

### 2.4 ★★ vLLM 的 Elastic EP 源码落点（已定位，2026-09-23）

**这就是你要移植的模板**，而且它就在本地 `code/vllm` 里（不是"未来要做的"，是已经写好的）。

| 职责 | 文件 |
|---|---|
| **成员状态机** | `vllm/distributed/elastic_ep/elastic_state.py` ⭐ 先读这个 |
| **执行逻辑** | `vllm/distributed/elastic_ep/elastic_execute.py` |
| **重配置**（缩容/扩容后怎么重排）| `vllm/model_executor/layers/fused_moe/eep_reconfigure.py` ⭐ |
| **专家映射管理** | `vllm/model_executor/layers/fused_moe/expert_map_manager.py` |
| **成员变更的实际调用点** | `vllm/distributed/device_communicators/all2all.py:439` `buffer.connect_ranks(ranks_to_connect)`<br>`:455` `buffer.connect_ranks(ranks_to_connect, activate=make_active)`<br>`:468` `buffer.disconnect_ranks(ranks_to_disconnect)` |
| **对外 HTTP 接口** | `vllm/entrypoints/serve/elastic_ep/middleware.py`、`api_router.py` ← ⚠️ 说明弹性操作是**对外暴露的 API**，不只是内部机制 |
| **DeepEP v2 接入** | `vllm/model_executor/layers/fused_moe/prepare_finalize/deepep_v2.py` |
| **EPLB** | `vllm/distributed/eplb/{eplb_state,eplb_communicator,rebalance_execute}.py`、`vllm/v1/worker/gpu/eplb_utils.py` |
| 配置/CLI | `vllm/config/vllm.py`、`vllm/engine/arg_utils.py`、`vllm/entrypoints/cli/serve.py` |

**⭐ 从这份文件清单能读出的架构分工**（直接可以照抄到昇腾侧）：

```
elastic_state.py      状态机：谁是 active、当前成员是谁
      ↓
elastic_execute.py    执行：scale_down / scale_up 的流程编排
      ↓
eep_reconfigure.py    重配置：成员变了之后专家/分片怎么重排
      ↓
expert_map_manager.py 映射：专家号 → 物理卡
      ↓
all2all.py          成员变更原语：connect_ranks / disconnect_ranks（落到具体后端）
      ↑
elastic_ep/middleware.py + api_router.py   对外 API（HTTP）
```

> 💡 注意 `connect_ranks(..., activate=make_active)` 这个参数——**支持"先连上但先屏蔽，之后再放行"**，这正是我们之前在 `doc/06` 里看到的 `nixl_ep` 那套"扩容时新 rank 先保持 masked 再手动 unmask"的用法。**这个设计值得照搬**。

## 3. SGLang 的 EEP（有实测数据，可作对标基线）

**参数**【多方印证】：
- `--elastic-ep-backend`（none | mooncake）
- `--moe-a2a-backend`（deepep | mooncake | nixl | **ascend_fuseep** | pplx | mori）
- `--ep-num-redundant-experts N`（**越大可容忍越多 rank 失效**）
- `--enable-elastic-expert-backup`（默认 False，**用 DRAM 备份专家权重做快速恢复**）
- 需配合 `--disable-custom-all-reduce`

**⭐ 实测数据**（LMSYS 博客 2026-03-25【多方印证】）：

| 指标 | 数值 |
|---|---|
| 配置 | 32 GPU（ep=dp=32）+ **256 冗余专家** |
| 可容忍失效 | **16 个 rank** |
| 中断时间 | **< 10 s**（单 rank 故障 6.8 s） |
| 对比全量重启 | **2–3 分钟** |
| 静态性能 | 与 DeepEP 持平 |

**论文**：**arXiv 2605.10670**《EEP: Surviving Partial Rank Failures in Wide Expert-Parallel MoE Inference》

> 🎯 **这组数字是你最该记住的对标基线**：容错要做到"**中断几秒、静态性能不掉**"。

## 4. ★ 昇腾侧的落点（对你最重要的一节）

### 4.1 vLLM-Ascend 的 MoE 通信接线【多方印证】

- `vllm_ascend/ops/fused_moe/moe_comm_method.py`：`MoECommType` = `ALLGATHER` | `MC2` | `ALLTOALL` | `FUSED_MC2`
- 选择逻辑在 `vllm_ascend/ascend_forward_context.py` 的 `select_moe_comm_method`
- **调用链**：
  ```
  vllm-ascend
     ↓ torch_npu 的 npu_moe_distribute_dispatch_v2 / npu_moe_distribute_combine_v2（旧版 _v1）
  CANN ops-transformer 仓的 mc2/moe_distribute_dispatch_v2（算子本体）
     ↓
  HCCL（通信）
  ```

⭐ **分层就此确认**：vllm-ascend **不自己实现 mc2**，而是经 torch_npu/ACLNN 调 CANN 算子。
→ **你要做弹性，最终必然碰到 `ops-transformer` 的 mc2 层** —— 也就是我在 `doc/04` §2.2 挖到 `elasticInfoOptional` 的那个地方。

（`dispatch_v2` 原型里含 `elastic_info`、`zero/copy/const_expert_num`；ops-transformer 侧有 `elastic_buff.py` 痕迹——**弹性语义未确认**）

### 4.2 昇腾现有的弹性线索

| 线索 | 说明 |
|---|---|
| EPLB | `eplb_swift_balancer` 文档：`DYNAMIC_EPLB` 或静态 `expert_map_path`；策略 `random` / `DefaultEplb` / `SwiftBalanceEplb` / `FlashLB`；文档称冗余专家放置能"提升硬件故障时的韧性" |
| **PR #8497** | **Elastic EP Milestone 2 适配** ← 昇腾已在跟进 vLLM 的 Elastic EP 议题 |
| `elastic_info` | `dispatch_v2` 原型里有，但文档标"当前版本不支持"（见 `doc/04` §2.2）|

❌ **但：未找到 vllm-ascend 的 elastic EP 用户文档或独立的容错/故障恢复实现**【待核实】

### 4.3 你的任务位置（推断，待导师确认）

> **把 GPU 侧已经跑通的 Elastic EP 路线（detect → scale_down → scale_up），在昇腾侧实现出来。**

| 层 | 你要碰的东西 | 现状 |
|---|---|---|
| **上层** | vLLM-Ascend 的 EP 接入 + 控制面 | 有 EPLB，无 elastic EP 落地 |
| **中层** | `npu_moe_distribute_dispatch_v2` 的 `elastic_info` 路径 | **代码在，接口标"不支持"** |
| **下层** | HCCL 的通信域缩容/重连 | **缺**（见 `doc/02` §5.5 缺口清单）|

## 6. 核实状态

### ✅ 已用源码核实（2026-09-23，`code/vllm-ascend` 已克隆）

| 结论 | 证据 |
|---|---|
| **`MoECommType` 就是 4 种**：`ALLTOALL` / `ALLGATHER` / `MC2` / `FUSED_MC2` | `vllm_ascend/ops/fused_moe/moe_comm_method.py:58-63` |
| **MC2 / FusedMC2 走 CANN 的 mc2 算子** | 同文件 `:215` `MC2CommImpl`、`:259` `FusedMC2CommImpl` 的类注释均写明依赖 `npu_moe_distribute_dispatch` / `npu_moe_distribute_combine`；`TokenDispatcherWithMC2` / `PrepareAndFinalizeWithMC2` |
| **vllm-ascend 里没有 elastic EP 实现** | 全仓搜 `elastic_info` / `elastic_ep` **无命中** |
| **EPLB 的落地位置** | `vllm_ascend/worker/eplb.py`、`worker/v2/eplb.py`、`patch/platform/patch_eplb.py` |

### ⚠️ ⚠️ 两个"名字骗人"的坑（务必记住）

1. **vllm-ascend 里搜到的 `elastic` 全是假的**：唯一的 `elastic` 命中在 `model_loader/netloader/`（`ElasticClient` / `ElasticServer` / `elastic_load`）—— 那是**模型权重的弹性 P2P 加载**，**和 EP 容错毫无关系**。
2. **release notes 里的 `EPLB (Elastic Prefill Load Balancing)`** 是 **Prefill 负载均衡**，**不是容错**。别被"Elastic"这个词带跑。

> 📌 这两条正好印证：**昇腾侧目前没有 EP 弹性容错的实现** —— 你的任务空间就在这里。
