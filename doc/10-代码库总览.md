## 0. 一句话总览

导师给的 10 个仓库，**通信相关的是 3 个（hccl / hcomm / hixl）**，但真正决定我们能不能做成的是 **hcomm**（通信域生命周期、故障检测、重试执行体全在这里）；`ops-transformer` 的通信算子在 `mc2/`（已有 `doc/04`）；其余 6 个是**底座**（driver / runtime）、**框架层**（torch_npu）、**集群容错调度**（mind-cluster）、**算子开发路线**（triton-ascend ×2）。

**本次最重要的三个发现**：

1. **⭐ 我们缺的"检测层"，昇腾侧其实有三套现成设施**（都在 [§四](#四跨库的五条结论对任务的影响)）：hcomm 的 `cluster_monitor`/`heartbeat`（30s LOST 阈值）、runtime 的异常回调（能区分本端/远端/链路故障）、mind-cluster 的集群故障检测（MindIO 心跳 2s，丢 3 次判异常）。
2. **⭐ "通信域缩容"在昇腾侧没有原生实现，但有三条可走的现实路径**：`HcclCreateSubCommConfig` 建子通信域、abort + 重建通信域、hcomm 的"等量替换"（`DiffRankUpdater`）。**没有 shrink/grow API**——`hcomm`、`hixl`、`torch_npu` 三仓 grep `shrink|elastic` 全部零命中。
3. **⚠️ 一批硬约束会直接否掉某些方案**（见 §四.3），比如：`hcomm` 的 `src/legacy/` **禁止新增特性**、A5（950）**不支持 Suspend**、OpRetry 与 AivMode **互斥**、torch_npu 的 ProcessGroup **出错即整进程 down 且 abort 后不可复用**。

## 一、10 个库各是什么（速查表）

| 库 | 一句话是什么 | 通信 | 容错 | 对我们的价值 |
|---|---|---|---|---|
| **hccl** | 集合通信**算子库**（AllToAll 等算子 + 算法层） | ★★★ | 有 OpRetry/Suspend 的**配置与入口**，执行体不在本仓 | 主战场之一，见 `doc/02` |
| **hcomm** | 通信**基础库**：通信域管理 + 传输原语 | ★★★ | **★ 全在这里**：Suspend/Resume、OpRetry 执行体、心跳、快照恢复 | **本次最大收获**，见 §三.2 |
| **hixl** | **单边**通信库（KV Cache 搬运 / PD 分离），**不是集合通信** | ★★ | 链路级心跳 + fail-fast + 自动重建；无 rank/无缩容 | 不是落点，但可借"链路自愈"原子，见 §三.3 |
| **ops-transformer** | 昇腾 transformer/MoE **算子库**；`mc2/` 是通信算子 | ★★★ | `moe_distribute_elastic.h` 缩容 kernel | 主战场之二，见 `doc/04` |
| **torch_npu** | PyTorch 的昇腾**后端插件**（`Ascend/pytorch`） | ★★ | PG 错误语义 + `reinit_process_group`/`resume_hccl_comm` 雏形 | ⭐ vLLM-Ascend 链上的**框架层落点**，见 §三.5 |
| **runtime** | CANN **运行时**（设备/流/内存/任务调度） | ★★ | ★ 异常回调 + 故障判定 + 快照恢复 + stream 级 abort/recover | ⭐ 提供"检测钩子"与故障判定输入，见 §三.6 |
| **driver** | CANN **驱动**（用户态 HAL + 内核态 .ko） | ★★ | 设备健康状态位 + 故障事件订阅 + 链路判据 | 只读 5%（故障判据的来源），见 §三.7 |
| **mind-cluster** | 昇腾**集群管理/容错调度**（22 个组件） | ★ | ★ 检测/分级/隔离/恢复**闭环**；弹性训练=**DP 域**缩容 | ⭐ 检测层可直接复用；缩容是训练向、非 EP，见 §三.8 |
| **triton-ascend** | Triton 的**昇腾后端** | ✗ | ✗ | 辅助提效（与 `doc/00` 结论一致） |
| **triton-ascend-ops** | Triton 昇腾**教学样例仓**（31 个文件） | ✗ | ✗ | 写 kernel 的范式参考，无通信/容错，见 §三.10 |

## 二、分层地图（谁在谁上面）

```
                      vLLM-Ascend（框架/调度层）            ← 落点：控制面
                              ↓ torch.ops.npu.* / dist.*
   torch_npu  ←───────── PyTorch 的昇腾插件（ProcessGroupHCCL 在这层！）   ← 落点：PG 层
                              ↓
   vllm_ascend 经 torch_npu 调 CANN 算子（见 doc/09 §4.1）
                              ↓
   ops-transformer（mc2/：dispatch、combine、alltoall 融合算子）          ← 落点：数据面
                              ↓ ACLNN / HCCL window + BatchWrite
   hccl（集合通信算子库）  ─── dlsym 弱符号 ───→  hcomm（通信域/传输/检测/重试）
                              ↓ aclrt*                      ↓ aclrt*
   ──────────────── runtime（流/内存/事件/异常回调/快照）────────────────
                              ↓ ascend_hal / ioctl
   ──────────────── driver（用户态 HAL + 内核态驱动）────────────────
                              ↓
                          910B / 910_93 / 950 硬件

   【旁路】hixl（单边通信）→ 依赖 hcomm + runtime，直接 dlopen libascend_hal.so
   【旁路】mind-cluster（集群层，K8s 侧）：检测节点/芯片/网络故障 → 决策恢复策略 → 通知框架
   【旁路】triton-ascend / triton-ascend-ops：算子开发路线（与通信链路无关）
```

**读图要点**：
- **hccl 与 hcomm 是"两个仓、一套库"**：官方原话是"HCCL = HCCL 算子库 + HCOMM 通信基础库"，两仓用 `dlsym` 解耦（`hcomm/AGENTS.md:9-10`）。**通信域建/删/挂起/恢复都在 hcomm**。
- **hccl/hcomm 都隔着 runtime**（调 `aclrt*`），**只有 hixl 直接 `dlopen` `libascend_hal.so`**（`hixl/src/hixl/proxy/ascend_hal_proxy.h:19-27`）——所以 driver 与 hixl 贴得最近。
- **runtime 反向依赖 HCCL**：AI CPU 调度侧动态加载 `HcclInitCsCommFunc/HcclAbortSelfFunc/HcclWaitSomeFunc`（`runtime/src/aicpu_sched/aicpu_schedule/common/aicpusd_hccl_api.cpp:24-38`）和 MC2 算子 `libhccl_operator_call.so`——**说明运行时层已经知道"通信算子"这回事**，是双向耦合。
- **mind-cluster 在 K8s 侧，不在进程内**（除了 MindIO TFT 是训练框架进程内的）。

### 3.2 hcomm（通信基础库）★ —— `doc/02` 的 TODO 由此补齐

**定位**：HCCL 的通信基础库，三层架构（`hcomm/AGENTS.md:13-15`；权威来源是 `hcomm/docs/zh/architecture/architecture-brief.md`）：
L1 算子层（`cann/hccl`）→ **L2 HCCM 通信域管理**（`hcomm/src/coll_communicator_mgr`）→ **L3 基础通信**（`hcomm/src/base_comm`：Endpoint/Channel/CommMem/CommEngine）。

**目录地图**：

```
hcomm/src/
├── base_comm/           # L3 数据面原语（primitives/ + resources/{endpoints,endpoint_pairs,reged_mems,ccu,hccp}）
├── coll_communicator_mgr/   # L2 通信域管理（HCCM）
│   ├── communicator/        # coll_comm（Suspend/Clean/Resume）+ device(aicpu)
│   ├── rank_info_detect/    # bootstrap / root_info 检测 / socket_agent
│   ├── rank_graph/          # 拓扑构建（phy_topo、rank_graph_builder、rank_table_info）
│   ├── team/                # ⭐ 子通信域（hccl/ 与 hcomm/ 两套 team）
│   ├── resource_mgr/        # local（StopLaunch/Clean/Resume）/ remote
│   └── dfx/                 # ⭐ cluster_monitor（新代心跳）、ns_recovery、taskException、rtsq_poll
└── legacy/                  # 历史兼容（⚠️ 禁止新增特性）
    ├── ascend910/           # A2/A3：op_base、communicator、cluster_maintenance（heartbeat、OpRetry、snapshot）
    └── ascend950/           # A5：communicator（含 fault_recovery 快照恢复）、framework
```

**① 通信域生命周期（Suspend/Resume）——答案在这里**：

| 平台 | 实现 | 关键点 |
|---|---|---|
| A2/A3 | `legacy/ascend910/framework/op_base/src/op_base.cc:5755 HcclCommSuspend` / `:5828 HcclCommResume` → `communicator/impl/hccl_communicator.cc:1042 Suspend` / `:2216 Resume` | 经 KFC 通道给 AICPU 背景线程下 `KfcCommand`、轮询 `KfcStatus`；有状态回调 `HcclCommRegCommStateCallback`（`op_base.cc:5784`）供上层在 RESUME_PRE/POST 前后做 reshard |
| 新代（HCCM） | `coll_communicator_mgr/communicator/coll_comm.cc:1053 Suspend` / `:1071 Clean` / `:1096 Resume` | 状态 `HCCL_COMM_STATUS_SUSPENDING`（`include/hccl/hccl_types.h:223-227`）；⚠️ **Suspend 成功返回 `HCCL_E_SUSPENDING`（非 0）**，上层必须当成功处理 |
| **A5（950）** | `legacy/ascend950/framework/communicator/communicator_impl.cc:1915 Suspend` / `:2032 Resume` / `:2178 RecoverComm` | ⚠️ **`HcclCommSuspendV2` 直接返回 `HCCL_E_NOT_SUPPORT`**（`op_base_v2.cc:1471-1473`，"V950 not support suspend"）；**A5 走的是"快照恢复"路线**：`HcclSnapshotSave`(:2739) / `HcclSnapshotRecoverAllComms`(:2815) / `RecoverComm`（重建 Notify/Stream/Socket/RmaConn/拓扑/算法组件…） |

**② OpRetry（算子重执行）执行体 —— 在 `legacy/ascend910/.../cluster_maintenance/recovery/operator_retry/`**（`doc/02` 里"待查"的那件事，已找到）：

- **架构**：Server-Agent 状态机。每个通信域注册一个 Agent（每 rank，独立线程）+ 一个 Server（仅 root rank）；**70+ 个状态**（`hccl_op_retry_pub.h:30-99 RetryState`）。
- **谁检测错误**：Agent 轮询 AICPU 状态与 RDMA CQE（1s 间隔）；心跳旁路也采集（`heartbeat.cc:1793 OpRetryCQEHandle`）。
- **怎么协商**：Server 收集全 rank 的 `RetryInfo`，校验算子标识一致/重试次数/链路状态（`opretry_base.h:142/168/169/171`），失败即上报故障。
- **怎么重下发**：`STOP_AICPU → STOP_STREAM → CLEAR_STREAM → STOP_TRANSPORT → RESET_NOTIFY → RESUME_TRANSPORT → CAN_RETRY`；最大重试 3 次（`opretry_base.h:23`）。
- **L0/L1/L2 的真实含义**（`legacy/ascend910/pub_inc/externalinput_pub.h:26-29`）：**server 内 / server 间 / 超节点间**（不是"L1/L2 两级开关"那么简单）。
- **借轨通信**：备网卡 IP 在 `rank_graph/hccl_rankgraph.h:25 backupDeviceIp`；落地 `hccl_communicator.h:451 SwitchNic`、`:665 PrepareLinkForSwitchNic`；⚠️ **发生借轨后不支持回切**（`opretry_base.cc:702`）。
- ⚠️ **A5 没有 OpRetry**：`legacy/ascend950/` 全目录 grep `OpRetry` **零命中**（待核实是否用 CCU/taskException 等价实现）。

**③ 故障检测（两代并存）**：

| 代际 | 位置 | 参数 |
|---|---|---|
| 一代 | `legacy/ascend910/framework/cluster_maintenance/health/heartbeat/` | 50ms 周期、1000ms 帧、**LOST 阈值 30s**、STUCK 5min；7 态状态机（`heartbeat.h:73-81`：OK/LOST/NOTIFY/CQE_ERR/OPRETRY_NOT_SUPPORT/STUCK/INCONSISTENT）|
| 二代 | `coll_communicator_mgr/dfx/cluster_monitor/`（含 README 时序图）| 双 Ring 建链、`lostThreshold_ = HCCL_LOST_THRESHOLD(30s)`；CQE 错误经构造函数回调上抛；**优先级 CQE_ERR > LOST** |
| 其他 | `detect_connect_anomalies`（白名单 + socket 探测）、`taskException`（device 任务异常上抛）、`rtsq_poll` | 见 `doc/02` |

**④ 没有 elastic / shrink / grow**：`grep -rniE "shrink|elastic"` **零命中**。有的是：
- **"等量替换"（换卡不缩容）**：`legacy/ascend950/framework/communicator/diff_rank_updater.cc:161 DiffRankUpdater`——读外部 JSON，只支持**整框替换**或 **64+1 替换**两种，rank 数量不变。
- **子通信域**：`coll_communicator_mgr/team/` + `HcclCreateSubCommConfig` —— **这是"缩容后继续"最现实的落点**（在原通信域上建一个排除故障 rank 的子域）。

**⑤ 对我们的意义（必须先动的模块，按依赖顺序）**：

1. **检测层**（改动小）→ 用二代 `cluster_monitor`；**缺的能力是把"rank 永久故障"与"瞬时可重试 CQE"区分开**，并把事件结构化上抛。
2. **安全中止** → `CollComm::Suspend()` + `Clean()`（唯一现成的"暂停并清干净"通道）。
3. **成员变更** → **无现成实现，必须新增**；可复用 `DiffRankUpdater`（替换语义）、`team/`（子集通信）、`rank_graph_builder.cc:773 RecoverBuild`（拓扑重建）。
4. **重新分片** → **hcomm 管不到**（它只到"通信域成员 + 拓扑 + 传输资源"），必须由 `ops-transformer` 的 dispatch/combine 做；hcomm 只需提供稳定的子通信域句柄 + 新 rank 映射查询。
5. **继续执行** → `CollComm::Resume()`；A5 走 `HcclSnapshotRecoverAllComms`。

### 3.3 hixl（单边通信库）★ 新

**是什么**：**HIXL = Huawei Xfer Library**，昇腾**单边通信库**（one-sided），主打 **KV Cache 搬运 / PD 分离 / RL 参数切换**（`README.md:31`）。官方定位："与集合通信库**并列**"（`docs/zh/design/llm-datadist_supporting_the_hixl_transfer_backend.md:5`）。
产物：`libcann_hixl.so` + `libllm_datadist.so`；**依赖 hcomm ≥ 9.1.0** + runtime；出口是代理层 `src/hixl/proxy/hcomm_proxy.h`。

**三条传输路径**（官方分诊文档 `hixl-transfer-paths.md:21-25`）：
① ADXL 直传（默认，底层是 **HcclComm**，`src/llm_datadist/adxl/`）② FabricMem（超节点统一编址 + SDMA，`src/hixl/fabric_mem/`）③ HIXL_CS（Client-Server，`src/hixl/cs/`）。

**API**：`RegisterMem` / `Connect(Async)` / `Transfer{Sync,Async}` / `SendNotify` / `GetCapability`（`include/hixl/hixl.h`）——**没有 rank、没有通信域、没有 collective**（grep `rank` 在 `include/hixl` 零命中）。

**容错相关（有，但只到"链路级"）**：
- 心跳 10s（引擎，`engine/client_manager.cc:21`）/ 120s（FabricMem 控制面，`fabric_mem_control.cc:44`）；API 全带 `timeout_in_millis`。
- **故障 → 链路标记不可用 → fail-fast 拒服务**：`CommChannel::FailChannel`（`adxl/comm_channel.cc:319-323`）。
- **自愈**：心跳失败 → `DestroyClient`；**下一次传输时 `AutoConnect` 按需重建**（`hixl_engine.cc:418-440`）——即"**abort + 重建**"的链路级对应物。
- 故障上报：hcomm 异常回调 `HcommExceptionRegisterCallback` → device 侧置 err_flag → 上报 TS（`src/ops/hixl_kernel/task_exception_handler.cc:99-137`）。

**⚠️ 对我们的三个警告**：
1. **它不是落点**：没有 AllToAll、没有 rank、没有通信域、没有缩容。
2. **它的"自愈"是点对点链路级的**，**不产生"全体 rank 的新成员视图"**——若误以为 hixl 断链自愈 = 容错完成，会出现**成员视图不一致**（部分 rank 走新链路、部分还在旧通信域）。
3. **检测时延太大**（10s/120s），且 `HcommExceptionRegisterCallback` 是 **weak symbol**——某些版本上直接收不到回调（`hcomm_proxy.cc:69-70`），必须做能力探测。
4. 文档里"面对集群节点动态扩缩容需求时可快速完成链路适配"是**宣传语**，代码侧只有 keepalive 断链 + 按需重建，**没有任何缩容实现**——引用时别当能力证据。

### 3.4 ops-transformer（通信算子）→ 详见 `doc/04`

- `mc2/` 目录地图、dispatch/combine 数据流、**elastic 缩容机制（`elasticInfoOptional` + `moe_distribute_elastic.h`）**、EPLB 相关算子都已在 `doc/04`。
- 与 `doc/09` §4.1 的调用链对齐：**vllm-ascend → torch_npu 的 `npu_moe_distribute_dispatch_v2` → ops-transformer 的 `mc2/moe_distribute_dispatch_v2` → HCCL**。

### 3.5 torch_npu（PyTorch 昇腾后端）★ 新 —— 框架层落点

**是什么**：PyTorch 的 Ascend 插件（PrivateUse1 后端），**仓库名是 `Ascend/pytorch`**；单源码树适配 torch 2.13/2.14/2.15/2.16（`version.txt`）。

**⭐ 关键结论：`ProcessGroupHCCL` 就在本仓实现**（不在 PyTorch 主仓的 c10d）：
- 实现：`torch_npu/csrc/distributed/ProcessGroupHCCL.cpp`（**7957 行**）/`.hpp`；另有低延迟后端 `ProcessGroupLCCL`。
- 注册：`torch_npu/_init/registry/distributed.py:34 register_distributed_backend_for_npu()` → 注册 `"hccl"` / `"lccl"` 后端。
- **AllToAll 实现位置**：`ProcessGroupHCCL.cpp:7410 alltoall_base()`（等分 → `hcclAlltoAll` :7483；不等分 → `hcclAlltoAllV` :7599）、`:7641 alltoall()`。⚠️ 文档标注 `all_to_all` 输入**仅支持 fp32**，且有兼容开关 `torch_npu.npu.use_compatible_impl(True)`（`docs/zh/api/native_api/pytorch_2-14-0/torch-distributed.md:682-728`）。
- **自定义通信算子模板**：`torch_npu/csrc/distributed/HcclOps.cpp`（`TORCH_LIBRARY(npu_custom_dist)`）——若要给 EP 写自定义 all2all，这是现成入口。

**⭐ 容错/弹性语义（很重要）**：
- 错误模式 `ErrorHandlingMode{NoHandling, TearDown, CleanUpOnly, SkipCleanUp}`（`.hpp:199-214`）；**默认 TearDown，一错就整进程 down**：`WorkHCCL::handleException()`（`.cpp:1038-1055`，"To avoid data inconsistency, we are taking the entire process down."）；开关 `TORCH_HCCL_ASYNC_ERROR_HANDLING`。
- **PG abort 后不能复用**：`abortCommsFromMap()`（`.cpp:1378-1416`）明确"用户负责 destroy 并 recreate PG"——**与 NCCL 语义一致**。
- **但已有"重建/恢复"的雏形（距我们的目标最近）**：
  - `abortAndClearHcclComm()`（`.cpp:1549`）：abort 并清空 comm 映射 → **允许重建**
  - `resumeHcclComm(device_id)`（`.cpp:3915`）→ `HcclCommResumeFace`：**不重建 comm 的链路恢复**
  - Python：`torch_npu.distributed.reinit_process_group(group, rebuild_link=True/False)`（`torch_npu/distributed/distributed_c10d.py:331-357`）
  - 设备级：`torch_npu.npu.restart_device()`（`torch_npu/npu/_recovery.py:59`）
  - 备链路：`_set_switch_nic_comm` / `_comm_switch_nic`
  - 状态落盘：`TORCH_HCCL_STATUS_SAVE_*`（失败现场）
- **没有 shrink API**；但 `HcclCreateSubCommConfig`（子通信域）**已在用**（`test/distributed/test_sub_comm_derivation.py`）。
- **必读目录**：`docs/zh/developer_notes/distributed/startup_and_fault_tolerance/`（官方 FT 文档）+ `docs/zh/developer_notes/fault_diagnosis/watchdog.md`。

**对任务**：torch_npu **不是透传层**——要改"通信行为"，PG 层是本仓的实体。缩容的现实约束是："HCCL 无成员变更 API → 走**建子域**或 **abort+重建** 两条路"，而 `abortAndClearHcclComm` + `resumeHcclComm` + `reinit_process_group` 就是可复用的骨架。

### 3.8 mind-cluster（集群管理与容错调度）★ 新 —— 检测层的答案

**是什么**：MindCluster（AI 集群系统软件）：NPU 集群**作业调度 + 运维监测 + 故障恢复 + 故障诊断**（`README.md:22-24`）。`component/` 下 **22 个子项目**，关键几个：

| 组件 | 作用 |
|---|---|
| `noded` | 节点侧异常检测（CPU/内存/硬盘/存储/**灵衢慢网络**）→ 上报 ClusterD |
| `ascend-device-plugin` | K8s device plugin：**芯片故障 + 参数面网络故障 + 任务卡死检测** |
| **`clusterd`** | **集群大脑**：汇总故障 → 分级 → 决策恢复策略 → gRPC 下发 |
| `ascend-for-volcano` / `ascend-operator` | 拓扑亲和调度 / 故障重调度；AscendJob CRD |
| **`mindio`** | **容错核心**：`tft`（训练容错：TTP/UCE/ARF）+ `acp`（Checkpoint 加速）|
| `infer-operator` | **推理** CRD：Pod 重调度 + 容器快照（CRIU）|

**⭐ 故障检测全景**（`docs/zh/scheduling/04_usage/04_fault_detection_and_diagnosis/01_working_principle.md:5-13`）：

| 检测对象 | 机制 | 周期/时延 |
|---|---|---|
| NPU 芯片 / 参数面网络 | DCMI 订阅 + 网关探测 + Linkdown 事件 | Linkdown ≤20s 降级、>20s 升级为故障 |
| 节点 CPU/内存/硬盘/存储 | NodeD（ipmi/iBMC）**ConfigMap 轮询** | 60s 轮询；变化 ≤5s 更新 |
| 灵衢（HCCS）超节点网络 | NodeD **pingmesh** | `task_interval` 1~60s |
| UB 网卡 | `hinicadm5` 周期检测 | — |
| **任务卡死（hang）** | Device Plugin 4 指标（AICore 利用率<5% / HBM 增量 / 网络流量 / CPU 时间），连续 5 次 | — |
| **训练 rank 心跳** ⭐ | **MindIO TFT**：gRPC 心跳，**2s 一次、丢 3 次判异常（≈6s）** | `controller.cpp:34-35 HEART_BEAT_MAX_LOSS=3 / TIME_CHECKER_INTERVAL=2000` |

> 💡 **`doc/02` 里"集群心跳机制存在但实现在别处"的答案**：心跳在 **MindIO TFT（C++，训练框架进程内）**；NodeD/DevicePlugin 的"心跳"其实是 ConfigMap 轮询，**不是网络心跳**。

**⭐ 恢复体系**：多层（Job 级重调度 → Pod 级 → 进程级 → **弹性训练（缩容）** → 进程级在线恢复 → 算子级在线恢复）；策略枚举在 `clusterd/pkg/common/constant/const.go:38-69`（`retry / recover-in-place / dump / exit / **elastic-training** / **downgrade** / upgrade / job-rescheduling / pod-rescheduling`）。

**⭐ 弹性训练 = 唯一真正的"通信域缩容"**（`docs/.../05_fault_recovery/01_resumable_training/.../01_fault_handling.md:834-1040`）：
- 场景：硬件故障且无备用资源时，**按数据并行（DP）域缩容**继续训练，有空闲资源再扩容。
- 流程：ClusterD → MindIO Controller → 各进程 Processor → **执行通信组重建**（`tft_register_rebuild_group_handler`，超时 180s；`TTP_MAX_COMM_GROUP_NUM=2000`）。
- ⚠️ **硬约束**：**仅 PyTorch + MindSpeed-LLM 2.3.0**、仅 acjob 训练任务；**rank0 故障不支持**；不支持 watchdog/多模态；缩容粒度是 **DP 域**（`{"scale-in-strategy": "DP"}`），**不是 EP**。

**⭐ EP 相关**：`component/clusterd/pkg/domain/epranktable/`（`ranktable_manager.go:171-199` 监听 Pod/CM 变化重算）+ `SubscribeRankTable` 流式推送（`config/grpc_service.go:81-110`）——**EP 的 rank table 通道已存在**，但它只重算成员拓扑，**不剔除故障 rank、不缩容**；全仓 **grep 不到"专家并行/EP 域"语义**（`MoE` 只在 MindIO 约束与模型名里出现）。

**推理侧**：vLLM/MindIE 走 `infer-operator` 的 **Pod 级重启重调度 + 容器快照**（warmup 后存 Host/Device 快照，启动 30min → 分钟级，CRIU 需 containerd 1.6+）；文档明确 **"故障场景下不支持自动或手动弹性扩缩容"**（`05_configuring_elastic_scaling.md:15`）。

**对任务的价值**：**检测层可直接复用**（芯片/网络/节点/卡死/心跳全都有，落 ConfigMap + ClusterD 汇总）；**控制面闭环可以注入一个新策略**（如 `ep-scale-in`）；但**缩容逻辑是训练向、DP 域的，且无 EP 语义**——EP 域的容错是**空白**，正好是我们的位置。

## 四、跨库的五条结论（对任务的影响）

### 1. 通信三件套的分工，决定了"要改哪里"

| 要做的事 | 落点 | 现状 |
|---|---|---|
| 通信算子 / 算法选择 / tiling | `hccl/src/ops/` | 开源、可改（`doc/02`）|
| 通信域建/删/挂起/恢复/拓扑重建/重试执行体 | **`hcomm`** | 有 Suspend/Resume/OpRetry/快照，**无缩容** |
| 单边传输（KV/PD 分离） | `hixl` | 与集合通信无关，**不是落点** |
| 集合通信的框架接口（PG 层） | `torch_npu` | 有 `reinit_process_group`/`resume_hccl_comm` 雏形 |
| EP dispatch/combine + elastic 适配 | `ops-transformer` | kernel 就绪、接口未开放（`doc/04` §2.2）|
| 框架调度/控制面 | vLLM-Ascend（+ mind-cluster 可选） | 无 elastic EP 落地（`doc/09`）|

### 2. "检测层"不缺基础设施，缺的是"判定永久故障 + 触发缩容"

现成的三处（可组合使用）：
1. **hcomm 内部**：`cluster_monitor`（30s LOST）+ heartbeat（CQE/LOST/STUCK）+ `detect_connect_anomalies`。
2. **runtime**：任务/设备/中止三类回调 + `RT_ERROR_LINK` + 链路错误三分（本端/远端/链路）。
3. **集群侧**：mind-cluster（芯片/网络/节点/卡死）+ MindIO 心跳（2s，丢 3 次）。

**缺口**：这三处都只到"报告状态"，**没有一处连到"把故障 rank 从通信域里剔除并重新分片"**——这正是 `doc/08` L2（补齐控制面）的实质内容。

### 3. 改代码前必须知道的硬约束（清单）

| 约束 | 出处 | 影响 |
|---|---|---|
| `hcomm/src/legacy/` **禁止新增特性**（只许修 bug/兼容）| `hcomm/AGENTS.md:48`（§3 架构约束表）| 新容错功能必须落 `coll_communicator_mgr/` 或 `base_comm/`，不能改 legacy |
| **A5（950）不支持 Suspend**，只有快照恢复 | `op_base_v2.cc:1471-1473` | 目标平台若是 950，先天缺一环 |
| **OpRetry 与 AivMode 互斥**（开 Aiv 会关掉 OpRetry）| `legacy/ascend910/framework/common/src/config.cc:608-612` | MoE EP 若用 AIV 展开 → 失去重执行能力 |
| **OpRetry 只覆盖"可重试故障"**，不覆盖 rank 永久退出 | `opretry_*`（收敛到 RETRY_FAIL，无降级缩容分支）| 我们要补的正是"永久退出"这条路 |
| `Suspend` 成功返回 **`HCCL_E_SUSPENDING`（非 0）** | `communicator_impl.cc:1936` | 上层不能把它当失败 |
| `HcclCommResume` 文档标注**"预留接口，不支持开发者使用"** | `hcomm/docs/zh/api_ref/comm_mgr_c/HcclCommResume.md:4` | 改造需自担变更风险 |
| torch_npu PG **出错默认整进程 down**，abort 后**不可复用** | `ProcessGroupHCCL.cpp:1038-1055 / :1378-1416` | "恢复"必须走 destroy+recreate 或子域 |
| `all_to_all` 在 torch_npu 里**仅支持 fp32**（有兼容开关）| `docs/zh/api/native_api/.../torch-distributed.md:682-728` | EP 的 fp8/bf16 token 不能走这条 |
| hixl 的 hcomm 异常回调是 **weak symbol** | `hixl/src/hixl/proxy/hcomm_proxy.cc:69-70` | 可能静默收不到故障回调 |
| mind-cluster 弹性缩容**只支持训练（PyTorch+MindSpeed-LLM）、只支持 DP 域** | `01_fault_handling.md:838-853` | 不能直接拿来给 EP 推理用 |

### 4. "通信域缩容"在昇腾侧的三条现实路径（按代价排序）

1. **建子通信域**（`HcclCreateSubCommConfig`）：保留原通信域、排除故障 rank 建子域——**代价最小、语义最干净**，且 torch_npu 已在用（`test_sub_comm_derivation.py`）。
2. **abort + 重建通信域**（`abortAndClearHcclComm` → `reinit_process_group`）：torch_npu 已有骨架，但**成员视图要全体协商**（谁还活着）。
3. **等量替换**（hcomm `DiffRankUpdater`）：换卡不缩容，支持整框替换 / 64+1 替换——**已有现成实现**，但 rank 数不变，解决不了"少一张卡"。

### 5. 我们的"位置"（与 `doc/09` 一致）

> **EP 域在挂卡后缩容继续** = 检测（可复用上述设施）→ 决策（**空白**，要新写控制面）→ 通信域收缩（**hcomm 无现成 API**，走①/②）→ **重新分片**（ops-transformer 的 dispatch/combine，**kernel 已就绪**）→ 继续推理。
