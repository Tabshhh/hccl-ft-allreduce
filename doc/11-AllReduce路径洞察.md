# 11 · AllReduce 路径与多层级组网洞察

> 目的：以 AllReduce 为入口，梳理从算子调用到设备互联、网络传输和大规模拓扑的完整路径，为 FT-AllReduce 设计确定故障边界与实验范围。
> 最后更新：2026-09-23

## 1. 先统一三个概念

- **AllReduce** 是集合通信语义：每个 rank 提供一份输入，所有 rank 得到规约结果。
- **通信层级** 是拓扑和软件对通信域的分段方式：例如服务器内、服务器间/超节点内、超节点之间。
- **RDMA/RoCE** 是传输方式。跨节点 AllReduce 经常使用 RDMA，但 AllReduce 本身不等于 RDMA，也不意味着每一段都走 RDMA。

## 2. 从源码确认的昇腾路径

HCOMM 的拓扑模型明确针对多级 AI 集群：一台服务器包含多个 NPU，多台服务器组成 Rack 或 SuperNode；拓扑由 rank、Fabric、Endpoint、Edge 和 Link 建模，并允许查询不同网络层级。

在 `CollAllReduceRingZerocopyExecutor` 的多超节点路径中：

1. `COMM_LEVEL0` 处理服务器内的 ReduceScatter/数据切分。
2. 单超节点时，`COMM_LEVEL1` 可以直接执行 AllReduce。
3. 多超节点时，`COMM_LEVEL1` 先完成超节点内/节点间的 ReduceScatter。
4. `COMM_LEVEL2` 执行超节点之间的 AllReduce。
5. 再由 `COMM_LEVEL1` 做 AllGather，恢复完整结果。

因此，多层级 AllReduce 常见结构是“近端先聚合 → 远端交换部分结果 → 近端展开”，而不是让所有 rank 在一个平面上直接组成大环。

## 3. 链路如何映射

链路取决于硬件代际和实际组网，不能只由算子名推断。典型映射如下：

| 距离 | 可能的互联 | 在 AllReduce 中的角色 |
|---|---|---|
| 同卡/片内 | 本地内存、片内引擎 | 本地拷贝或规约 |
| 同服务器 | HCCS、PCIe、SDMA 等 | Level 0 或近端子通信域 |
| 同超节点的服务器之间 | UB/HCCS 或 RoCE，取决于产品和布线 | Level 1 的局部聚合 |
| 超节点/服务器之间 | RoCE 或 InfiniBand 等 RDMA 网络，也可能有 TCP fallback | Level 2 的远端 AllReduce |

HCOMM 源码同时保留 TCP 与 RDMA 的远端协议类型；因此应在实验日志中记录最终选择的协议、Endpoint/Channel 类型和实际拓扑，而不是把“RoCE 组网”当作已经证明了算子必走 RDMA。

## 4. “万卡/十万卡是否走 RDMA”的准确表述

可以确认的工程判断是：在大规模多节点训练集群中，跨服务器、跨机架或跨超节点的数据交换通常需要高速网络，RoCE/InfiniBand 这类 RDMA 传输是常见选择；但是否使用 RDMA 仍由网络设备、通信库、环境变量、拓扑和 fallback 策略共同决定。

“跨集群”若只是一个作业内的多个超节点，通常仍可理解为同一训练通信域里的远端层；若是两个独立管理、网络隔离或地理分离的集群，则不能假设它们能直接组成一个 RDMA AllReduce，必须先确认互联、寻址、流控和通信库支持。

## 5. 层级名称不要混用

工作区出现三种不同语境：

| 语境 | 含义 | 用途 |
|---|---|---|
| HCOMM 软件架构 L1/L2/L3 | 算子层 → 通信域管理 → 基础通信资源 | 确定代码修改位置 |
| HCCL 算法 `COMM_LEVEL0/1/2` | 服务器内、服务器/超节点内、超节点间等拓扑子域 | 确定算法阶段和链路 |
| 拓扑模型 Layer 0/1/... | rank graph 中的网络层级，层内可为 FullMesh、Clos 等 | 描述组网和路径 |

FT-AllReduce 设计文档应同时写“软件层”和“拓扑层”，并在首次出现时明确命名。向导师确认时直接问：他说的 L1/L2/L3 是 HCOMM 软件层、HCCL 算法层，还是网络拓扑层。

## 6. scale-up 的工作语境

在弹性通信/EP 代码中，`scale_down` 表示移除成员并按新规模继续，`scale_up` 表示加入新 worker 或恢复成员、同步状态后提交新规模；这是通信域成员变化语境。在系统架构语境中，scale-up 也可能指单体系统增加资源，scale-out 指增加服务器。因此本项目记录时使用“成员扩容/恢复”或“集群扩展”，避免只写 scale-up。

## 7. 对 FT-AllReduce 的直接启示

故障注入和容错设计必须标注故障发生在哪个层级：服务器内链路、服务器间 RoCE、超节点间 RoCE，还是上层进程。不同层级会影响可见错误（CQE、超时、心跳）、可重试范围、是否能借轨，以及通信域重建的成员集合。

第一版原型只需锁定一个可控场景：两个服务器/超节点之间的 RoCE AllReduce，采用 fail-stop 或 CQE 错误模型，验证“检测 → 安全停止 → 成员重建/重试 → 后续 AllReduce”闭环。更高层级和十万卡路径先形成分析文档与待核实清单。

## 8. 尚未能由本地源码确认的事实

- 目标生产集群在万卡、十万卡规模下的确切物理拓扑、交换机层次和 RDMA 开关配置。
- 目标昇腾型号对 UB、RoCE、HCCS 的具体优先级和算法选择规则。
- 导师所说 L1/L2/L3 的准确术语来源。
- scale-up 是弹性成员恢复，还是组网架构扩容。

这些问题应在与导师对齐后补入本文档，不能用通用集群经验替代。
