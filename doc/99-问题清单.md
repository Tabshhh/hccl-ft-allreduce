### A7 🆕 容错的"控制面"允许放在哪一层？
候选：(a) vLLM-Ascend 进程内（框架层）；(b) **mind-cluster**（K8s 侧，现成的检测 + 分级 + 恢复闭环）；(c) HCCL/hcomm 内部（通信库自己决策）。

### A8 🆕 是否接受用"**建子通信域**"实现缩容（而不是改通信域 rankSize）？

### E2 ✅ 已解决（2026-09-23）：HCCL 的 OpRetry 执行体在 hcomm 里
**位置**：`hcomm/src/legacy/ascend910/framework/cluster_maintenance/recovery/operator_retry/`（8 个源文件）。
**机制**：Server-Agent 主从状态机（每 rank 一个 Agent 线程 + root rank 一个 Server），70+ 状态；Agent 轮询 AICPU 状态 / RDMA CQE（1s 间隔）发现错误 → Server 收齐全 rank `RetryInfo` 并校验（算子标识一致 / 重试次数 / 链路状态）→ 下发 `STOP_AICPU → STOP_STREAM → CLEAR_STREAM → STOP_TRANSPORT → RESET_NOTIFY → RESUME_TRANSPORT → CAN_RETRY`；**最大重试 3 次**（`opretry_base.h:23`）。
**L0/L1/L2 的真实含义**：**server 内 / server 间 / 超节点间**（`legacy/ascend910/pub_inc/externalinput_pub.h:26-29`），不是"两级开关"。
**借轨通信**：`SwitchNic`（`hccl_communicator.h:451`）、备网卡 IP `backupDeviceIp`（`rank_graph/hccl_rankgraph.h:25`）；⚠️ **借轨后不支持回切**（`opretry_base.cc:702`）。
⚠️ **A5 没有 OpRetry**（`legacy/ascend950/` 零命中，待核实是否有等价物）；⚠️ **与 AivMode 互斥**（`legacy/ascend910/framework/common/src/config.cc:608-612`）——MoE 若用 AIV 展开会失去重执行能力。

### E3 ✅ 大部分解决（2026-09-23）：Suspend/Resume 的实现在 hcomm，分两代 + 两条平台路线
- **A2/A3**：`legacy/ascend910/framework/op_base/src/op_base.cc:5755 HcclCommSuspend` / `:5828 HcclCommResume` → `communicator/impl/hccl_communicator.cc:1042 Suspend` / `:2216 Resume`（经 KFC 通道下 `KfcCommand` 给 AICPU 背景线程）；有状态回调 `HcclCommRegCommStateCallback`（`op_base.cc:5784`）供上层在 RESUME_PRE/POST 前后 reshard。
- **新代（HCCM）**：`coll_communicator_mgr/communicator/coll_comm.cc:1053 Suspend` / `:1071 Clean` / `:1096 Resume`；⚠️ **Suspend 成功返回 `HCCL_E_SUSPENDING`（非 0）**。
- **A5**：`HcclCommSuspendV2` **不支持**（`op_base_v2.cc:1471`）；A5 走**快照恢复**：`HcclSnapshotSave` / `HcclSnapshotRecoverAllComms` / `RecoverComm`（重建 Notify/Stream/Socket/拓扑/算法组件）。
- **与 NCCL 的对应关系**：HCCL 的 Suspend/Resume = "暂停 + 清干净 + 恢复"，而 **NCCL 的 Suspend/Resume 是显存 offload，不是一回事**（见 E-check 在 `doc/05`）；NCCL 的 shrink/grow 在 HCCL 侧**没有对应物**。
**仍未查清**：在途传输在 Suspend/Clean 时的处理细节；`HcclCommResume` 在"某 rank 永久失效"时是否可用；快照 buffer 的规模上限（大 AllToAll 中间态能否装下）。

### E4 🔄 elastic 机制（2026-09-23 大部分已查清）
**已查清**（详见 `doc/04` §2.2）：
- 接口是 `elasticInfoOptional`，shape `{4 + EP_WORLD_SIZE * 2}`；常量 `ELASTIC_INFO_OFFSET=4`、`RANK_LIST_NUM=2`、`EP_WORLD_SIZE_IDX/SHARE_RANK_NUM_IDX/MOE_NUM_IDX=1/2/3`
- **kernel 是"被动适配"**：`isScalingDownFlag_` 为真时读新的 world size / 专家数，并用 `elasticInfo[4 + 旧epRankId]` 做 **rank 重映射**，然后重算 `moeExpertNumPerRank`
- **决策不在 kernel 里** → 控制平面在 host/框架侧（这正是 `doc/07` 假设的"控制面/数据面分离"的现成范例，**那张 RANK_LIST 就是缩容后的重分片映射表**）

**仍未查清**：

### E6 ✅ 新增（2026-09-23）：检测层的三处现成设施与缺口（跨库结论）
**三处设施**（`doc/10` §四.2）：① hcomm `cluster_monitor`（30s LOST）+ heartbeat（CQE/LOST/STUCK）+ `detect_connect_anomalies`；② runtime 三类异常回调 + `RT_ERROR_LINK` + 链路错误三分（本端/远端/链路，`ccu_device_error_proc.cc:133-156`）；③ mind-cluster（芯片/网络/节点/卡死检测 + **MindIO 心跳 2s、丢 3 次判异常**）。
**缺口**：三者都只"报告状态"，**没有任何一处连到"剔除故障 rank + 重新分片"** → 这正是 `doc/08` 的 L2（补控制面）。
